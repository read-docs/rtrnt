# rtrnt roadmap

Each phase builds on the one before. Items link to the relevant BitTorrent Enhancement Proposal (BEP) where one applies.

## Phase 1: Hardening ✅

Make the existing download path correct and robust.

- [x] **Info hash from raw bytes**: hash the exact `info` bytes (`bencode::info_span`). Re-encoding the parsed struct dropped unknown keys such as `private`, which gave a wrong hash.
- [x] **Pieces are never lost**: a failed or abandoned piece goes back to the queue through an RAII claim. Before, one error left a permanent hole in the file.
- [x] **Peer bitfield tracking**: Bitfield and Have messages are recorded, and peers are only asked for pieces they have.
- [x] **Timeouts everywhere**: connect, handshake, read, write, unchoke and UDP tracker (with retries). A silent peer can no longer hang the client.
- [x] **Choke handling**: a choke mid-piece drops the piece back into the queue and waits for an unchoke.
- [x] **Safe message parsing**: frame size cap, exact-length checks, unknown message IDs skipped, block bounds validated. A malicious peer can no longer cause a panic or a 4 GB allocation.
- [x] **Request pipelining**: 16 outstanding block requests per peer.
- [x] **Disk storage**: verified pieces are written straight to disk (no whole file in RAM). Multi-file torrents are supported, and path traversal (`..`, absolute paths) is rejected.
- [x] **Trackers**: tries `announce` then all `announce-list` URLs. UDP: fixed short-read check, announce field order, retries, larger buffer, error action. HTTP: failure reason, compact and dict peer lists, `peers6`, request timeout.
- [x] **CLI and UX**: clap arguments, `tracing` logs (`RUST_LOG`), indicatif progress bar, random peer id.
- [x] **Tests**: unit tests per module, plus a loopback integration test against a mock seeder that chokes once and sends a corrupt block.

## Phase 2: Download engine

Faster, steadier downloads in real swarms.

- [x] **Rarest-first piece selection**: piece availability is counted across connected peers (Bitfield, Have, disconnects), and each peer claims the rarest piece it has, with random tie-breaks.
- [x] **Endgame mode**: once every remaining piece is in flight, idle peers also download those pieces, starting with the one fewest peers are on. The first verified copy wins, and the others send `Cancel` for their outstanding blocks. A stalled peer no longer holds up the finish. (This works per piece; per-block endgame is not done.)
- [x] **Peer pool and replacement**: every tracker peer is kept in a pool, and a worker that dies is replaced by the next one. Failed peers are retried with exponential backoff (30 s, 60 s) and dropped after 3 failures in a row; a peer that delivered a piece starts counting again. Peers that send corrupt or invalid data are banned. When the download completes, workers still connecting are aborted after a short grace period.
- [x] **Periodic re-announce**: the tracker is announced to again on its `interval`, kept between 60 s and 2 h and never shorter than `min interval`. Each announce runs in the background and reports real `downloaded`/`left` counts, and the peers it returns join the pool. When the pool runs dry, the tracker is asked once more, as early as `min interval` allows, before the download gives up. At exit the tracker gets `completed` (if the download finished) and then `stopped`, with a 10 s limit on both.
- [x] **Tracker tiers ([BEP 12](https://www.bittorrent.org/beps/bep_0012.html))**: `announce-list` is kept as tiers and replaces `announce` when present. Each tier is shuffled once at startup. Tiers are tried in order, and the tracker that answers moves to the front of its tier, so re-announces and the final `completed`/`stopped` go to it first. (One deviation: when looking for peers, a tracker that answers with none is passed over for the next one.)
- [x] **Keep-alives and interest**: a keep-alive goes out on any connection we have not written to for 90 s, under the usual 2-minute peer timeout. We are `Interested` only while a peer has a piece we still need, including one another peer is downloading, and send `NotInterested` once it has none. Waiting for an unchoke is part of the worker's idle wait, so a choked worker notices when its pieces arrive from elsewhere. A peer is dropped after 60 s choked while we are interested, or after 2 minutes with nothing we need. A peer that has something we need, even if we cannot claim it right now, is kept.
- [x] **Adaptive pipeline depth**: each peer's request queue holds about 3 s of its measured download rate, between 2 and 250 blocks (4 to start). The rate is measured over 1 s windows, and time spent choked or with nothing to request does not count against it. Requests now span pieces: a worker claims another piece when every block of the pieces it holds has been requested, so the pipeline no longer drains at each piece boundary. A slow peer gets a short queue and so holds few pieces. (The cap is a conservative 250, lowered to a peer's `reqq` when its extension handshake gives one; a peer that allows more still gets at most 250.)
- [x] **Cached file handles** in `Storage`: files are opened once and kept in a cache of up to 64 handles, least recently used out first, so a torrent with thousands of files stays well under the descriptor limit. Reads and writes use positional I/O (`pread`/`pwrite`), so concurrent piece writes share a handle without seeking and the cache lock is held only for the lookup.

## Phase 3: Persistence

- [x] **Resume**: at startup, pieces that overlap a file that already had data are hashed (on up to 4 threads, with a progress bar), and those that match are marked done. Pieces lying entirely in newly created files are skipped, so a new download starts at once. The tracker hears the real `left`, the progress bar starts at the data already on disk, and a download that is already complete exits without contacting the tracker.
- [x] **Resume file**: each torrent has `<info hash in hex>.resume` in `$XDG_STATE_HOME/rtrnt/resume/` (`~/.local/state/rtrnt/resume/` when that is unset, on macOS too), bencoded, outside the download directory. It holds a version, the info hash, the absolute output directory, a bitfield of the pieces verified and written, and each file's size and modification time as they were when it was saved. At startup a file that is clean (same size and time) vouches for the pieces in the bitfield that lie only in clean files, so they are not hashed; a piece that touches any other file is hashed if it overlaps data that was on disk, and pieces in clean files that the bitfield does not list are zeros we pre-allocated, so they are skipped. A clean exit therefore rehashes nothing, a crash rehashes only the files written since the last save, and so does an edit from outside. A missing, unreadable or truncated file, one for another info hash, output directory, version or file count, and `--recheck` (command line only) fall back to hashing as before, and the file is then written afresh. It is saved after the startup check (so a torrent that is complete on disk gets one too), every 30 s from the download loop if a piece completed since the last save, and once at exit, whether the run completed, was interrupted or failed, after the workers have drained. The write is atomic (a temporary file renamed over the old one) on the blocking pool, a failure is logged and the download goes on, and the file is kept after completion so a seed restarts at once. `--check` never reads it. Magnet links use it too. (Pieces are only written once verified, so blocks of a partly downloaded piece are not saved; a write that is still running when a periodic save looks at the files within the clock's resolution may go unnoticed until the next save.)
- [x] **`--check` mode**: verify a finished download against the torrent. Files are opened read-only and nothing is created or resized. Every piece whose bytes are all on disk is hashed, and each file is reported as missing, the wrong size, or with its number of bad pieces (a piece spanning two files counts against both). The exit code is non-zero unless every piece is intact.
- [x] **Graceful shutdown**: on Ctrl-C the piece queue closes and workers exit at their next wait. A worker writing a piece finishes the write first, and a worker aborted after the 2 s grace period cannot tear a write, because writes run to the end on the blocking pool. The tracker gets `stopped` (with the real `downloaded`/`left`), the progress bar stays where it was, and the exit code is 130. A second Ctrl-C quits at once. The handler is installed when the data on disk starts to be checked, or, if there is none to check, at the first announce, so Ctrl-C during a check stops it at the next piece, while Ctrl-C during the first announce of a torrent with nothing to check still kills the process at once. (Blocks of partly downloaded pieces are lost.)

## Phase 4: Seeding

Give back to the swarm.

- [x] **Listen for incoming peers** on `--port` (default 6881), over IPv4 and IPv6. If the port is taken, a free one is used instead, and trackers are told the port actually bound. Peers that connect to us and ask for our torrent are downloaded from like any other, while there is room under `--max-peers`. A peer is used over one connection at a time, so one we connect to that also connects to us is only downloaded from once. Our own address, which trackers list, is recognized by our peer id and never connected to again. An incoming peer that misbehaves is banned by IP.
- [x] **Serve requests**: every peer gets our `Bitfield` right after the handshake (left out while we have no piece) and a `Have` for each piece as it completes, unless it has that piece itself. Requests are answered from disk on the blocking pool, in the order asked, while the peer is unchoked. Before each block goes out, the worker handles the messages that have already arrived (up to 16 in a row), so a `Cancel` drops a queued request that was not sent yet. Up to 500 requests are queued per peer (the `reqq` we advertise), and any more are dropped. A request for a piece we do not have, for a range outside the piece, or for more than 16 KiB (what every client asks for; some allow up to 128 KiB) gets the peer banned. Requests that arrive while we choke the peer are ignored, and choking it drops its queue. A connection is kept while either side wants something from the other.
- [x] **Choking algorithm**: tit-for-tat with 4 regular unchoke slots, dealt every 10 s to the interested peers that sent us the most data over the last round, or, once we are seeding, that we sent the most. A fifth, optimistic slot goes to another interested peer at random and moves on every 30 s, so new peers get a chance to show what they can do. Peers with equal rates keep the order they connected in, so ties do not shuffle the slots. Between rounds the slots are dealt again, with the last round's rates, whenever a peer leaves or its interest changes, so a new peer is served and a freed slot is refilled at once. Who gets a slot is a pure function of the peers' rates and interest and the current optimistic peer. (There is no anti-snubbing, and new peers are not favored for the optimistic slot as in the original client.)
- [x] **Upload stats and seeding limits**: block bytes sent to peers are counted and reported as `uploaded` on every announce. With `--seed-ratio <RATIO>` or `--seed-time <MINUTES>`, a finished download keeps seeding until we have uploaded that many times the torrent's size this session, or for that long, whichever comes first, or until Ctrl-C (which then exits successfully). Both default to 0, which exits at completion as before. While seeding, the tracker hears `completed` at once rather than at exit, running out of peers no longer ends the run, new peers are still connected to and accepted, a peer that is a seed too is let go, and the progress bar shows the upload. A download that is already complete on disk announces itself as a seed (`left=0`, and never `completed`) and waits for peers even if the tracker lists none. (The ratio is measured against the torrent's size rather than `downloaded`, so a resumed download still gives back its share; limits are checked once a second.)

## Phase 5: Trackerless and extensions

- [x] **Extension protocol ([BEP 10](https://www.bittorrent.org/beps/bep_0010.html))**: our handshake sets reserved bit 20, and when the peer sets it too, our extension handshake follows at once with our client name and version (`v`), listen port (`p`), request queue size (`reqq`, 500) and the peer's address as we see it (`yourip`). The peer's extension handshake is kept on the connection, its client name is logged, and a later one updates it. Its `reqq` caps how many requests we keep in flight to that peer. Parsing is lenient: unknown keys, and known keys with the wrong type or an out-of-range value, are ignored, but a payload that is not a bencoded dictionary gets the peer banned. The connection can look up the id a peer wants for an extension name and send an extended message under it. Our `m` lists `ut_pex` (id 1, left out for private torrents) and `ut_metadata` (id 2), and our handshake carries `metadata_size` whenever we have the info dict. (Extended messages of other extensions are ignored.)
- [x] **Magnet links ([BEP 9](https://www.bittorrent.org/beps/bep_0009.html))**: the torrent argument may be a magnet link. Its info hash (`xt=urn:btih:`, 40 hex digits or 32 base32 characters, either case) is required, and `dn`, every `tr` (each tracker in a tier of its own, as libtorrent does) and `x.pe` peer addresses are read, percent-decoded; a link without a v1 info hash, with two different ones or with a malformed one is rejected with the reason. Peers come from the trackers (told `left=16384` until the size is known, as libtorrent does), the `x.pe` peers, the DHT and peers that connect to us, under `--max-peers`, with the same backoff, bans and "ask once more when out of peers" as a download. Every peer that lists `ut_metadata` and a `metadata_size` (up to 16 MiB) is asked for up to 4 pieces of 16 KiB at a time, the pieces fewest other peers were asked for first; one that rejects a request, lacks the metadata, disagrees on its size or stalls for 20 s is dropped and retried later. The pieces are put together from all peers and checked against the info hash. A bad copy from a single peer gets it banned; a bad copy from several throws the pieces away and from then on takes each copy from one peer at a time, so the liar is found. A piece of the wrong length or `total_size` gets its sender banned at once. The open connections then carry on into the download: Bitfield, Have and the fast extension's Have All, Have None and Allowed Fast messages that came before the piece count was known are applied then, and the peers get a new extension handshake with our `metadata_size`. With the fast extension we say Have None during the fetch, so pieces we turn out to have on disk follow as Have messages, and a peer that is just starting gets our allowed fast set at the handover. The metadata is saved, with the link's trackers, as `<info hash in hex>.torrent` in the output directory, so a later run with the same link (or `--check`, which otherwise fails, saying so) uses it; `--scrape` works from the link's `tr` list. We serve `ut_metadata` ourselves: `m` lists it (id 2), `metadata_size` is sent whenever we have the info dict, and requests are answered from its exact bytes, or rejected while we have none. A private torrent fetched this way stops using the DHT once its metadata says so. (`x.pe` host names are skipped, as only IP literals are used; a run that finds a saved `.torrent` uses its trackers, not the link's; the v2 `urn:btmh` hash is not supported; metadata requests are not rate limited.)
- [x] **DHT ([BEP 5](https://www.bittorrent.org/beps/bep_0005.html))**: a DHT node runs on UDP next to the TCP listener, on the same port when that is free, and bootstraps from `router.bittorrent.com`, `dht.transmissionbt.com` and `router.utorrent.com` with a `find_node` lookup for its own id. The routing table has k-buckets of 8, and only the bucket holding our own id splits. Only nodes that answer our queries are added, so a node that queries us (or that a peer names in a `Port` message) is pinged first. A full bucket keeps newcomers as replacements and pings its least recently seen node once it has not been heard from for 15 minutes, evicting it if it does not answer; a node that fails 2 queries in a row is replaced. Buckets unchanged for 15 minutes are refreshed. Queries time out after 2 s and are sent twice. The torrent is looked up with an iterative `get_peers` (3 queries in flight, a slow one stops counting after its first timeout, done once the closest 8 nodes have answered, at most 30 s) at the start and every 5 minutes, and the peers found join the pool. Afterwards our listening port is announced to the closest nodes that sent a token, with `implied_port` when TCP and UDP share the port. We answer `ping`, `find_node`, `get_peers` and `announce_peer`; tokens are tied to the asker's IP, with a secret that changes every 5 minutes (the previous one is still accepted), and announced peers are kept for 30 minutes, up to 200 per torrent and 1000 torrents. A torrent without trackers, or whose trackers return no peers, downloads from DHT peers alone, and when out of peers the DHT gets two more lookups before the download gives up. Peers that set the DHT handshake bit are sent our `Port`. Private torrents (BEP 27) never use the DHT, and `--no-dht` (or `dht = false` in the config file) turns it off. (IPv4 only. The routing table is not saved between runs, the node id is random rather than derived from our IP (BEP 42), and incoming queries are not rate limited.)
- [x] **Peer exchange ([BEP 11](https://www.bittorrent.org/beps/bep_0011.html))**: our extension handshake offers `ut_pex` (under id 1). Every peer that offers it too is told about the other peers we are connected to whose listening address we know: the address we connected to, or, for a peer that connected to us, its IP with the `p` port from its extension handshake. A peer whose port we do not know is never mentioned, and no peer hears about itself. The first message goes out as soon as there is a peer to tell about, and then one every 60 s with the peers added and dropped since the last, at most 50 of each (what does not fit goes in the next message), IPv4 and IPv6 in their own keys. An added peer carries the seed flag once its pieces show it has them all, and the reachable flag if we connected to it. Messages from peers are parsed leniently, like the extension handshake: missing or ill-typed keys, partial addresses and missing flags are ignored, and only a payload that is not a bencoded dictionary gets the peer banned. Of the peers a message adds, only the first 50 are looked at. Implausible ones (port 0, unspecified, multicast or broadcast addresses), the sender itself, and seeds once we are seeding are skipped, and the rest join the pool like tracker and DHT peers, as long as fewer than 500 peers are waiting there. A message that comes within 30 s of the last one taken from the same peer is ignored, so a peer cannot flood us. Private torrents (BEP 27) neither offer peer exchange nor act on its messages. (Dropped peers we hear of stay in the pool, and the reachable flag does not move a peer up in it. We never set the encryption, uTP or holepunch flags, and a peer already listed is not listed again when its flags change, for example when it becomes a seed.)
- [x] **Fast extension ([BEP 6](https://www.bittorrent.org/beps/bep_0006.html))**: our handshake sets reserved bit 0x04 of the last byte, and with a peer that sets it too, the five fast messages may be sent; a peer without the bit that sends one is banned. Right after the handshakes we send `Have All` or `Have None` in place of a `Bitfield` when we have every piece or none, and take a peer's like a `Bitfield`. Every request we do not serve gets a `Reject`: one that arrives while we choke the peer, one dropped because 500 are already queued, one dropped when we choke the peer (after the `Choke`), and one the peer cancels before its block went out. A request for a piece we lack or an invalid range still gets the peer banned. When a peer chokes us, our requests stand until it answers each with the block or a `Reject`. A rejected block is asked for again, at once if we are unchoked; while choked, a held piece we may not ask for goes back to the queue, for any peer, once nothing of it is outstanding. A `Reject` for a request we never sent bans the peer, except for requests we cancelled, which are remembered until answered, since the peer still answers them. A peer whose first `Bitfield`, `Have All` or `Have None` shows fewer than 10 pieces (and not all of them) gets our allowed fast set: 10 pieces worked out as BEP 6 says from its IPv4 /24 and the info hash (`fast::allowed_fast_set`, checked against the BEP's test vectors), or every piece of a torrent with no more than 10. For an IPv6 peer, which BEP 6 does not cover, its /48 is hashed instead. Its requests for those pieces are served while it is choked, and stay queued when we choke it. The pieces a peer allows us are asked for while it chokes us, until it rejects one of them while still choking us. `Suggest Piece` is accepted and ignored: rarest first picks our pieces. Peers without the bit are treated as before. (`Have All`, `Have None` and `Bitfield` are accepted at any time, not only first, and our extension handshake goes out before ours. The allowed fast set is offered once, when the peer first lists its pieces, and honoured for the whole connection, even once the peer has more than 10 pieces. A block that was never requested is ignored rather than closing the connection as BEP 6 asks, and a peer that rejects every request while unchoking us is asked again every time.)
- [x] **UDP tracker scrape and IPv6 listening**: `--scrape` asks every tracker of the torrent for its seeder, leecher and completed counts, prints one line per tracker, tier by tier, and exits. The exit code is non-zero unless a tracker answered. Every tracker is asked, not just the first to answer, because tiers often keep separate swarms. They are all asked at once, so a dead tracker costs its timeout only once. UDP scrape ([BEP 15](https://www.bittorrent.org/beps/bep_0015.html)) reuses the connect and retry logic of announces and sends up to 74 info hashes per request. HTTP scrape ([BEP 48](https://www.bittorrent.org/beps/bep_0048.html)) was added too: the scrape URL comes from the announce URL, and counts are read from the `files` dict. Incoming peers are also accepted on an IPv6-only `[::]` listener, on the port the IPv4 one got, and go through the same IP bans and `--max-peers` limit. Without IPv6 we listen over IPv4 only. Outgoing connections already handled IPv6 peers from `peers6` and from UDP trackers reached over IPv6. (An HTTP tracker whose announce URL does not end in `announce`, or `announce.php` and the like, cannot be scraped. We send no `ipv6=` to HTTP trackers, because there is no clean way to find our global IPv6 address; a tracker reached over IPv6 sees it anyway. An IPv6 peer is banned by its exact address, not its /64.)

## Phase 6: User experience

- [x] **Config file**: settings are read from the TOML file given with `--config`, or else from `$XDG_CONFIG_HOME/rtrnt/config.toml` (`~/.config/rtrnt/config.toml` when that is unset), on macOS too. The keys are the long option names: `output`, `max-peers`, `max-connections`, `port`, `seed-ratio`, `seed-time`, `max-download-rate` and `max-upload-rate`, plus `dht`, which `--no-dht` sets to false (and `--dht` back to true, so a file's `dht = false` can be overridden; of the two flags the last one given wins). A command-line flag beats the file, and the file beats the built-in default, even when the flag says 0 or off; `--print-config` prints the effective settings and where each came from. A leading `~` in `output` is expanded. An unknown key or a value of the wrong type, such as a negative or infinite `seed-ratio`, is an error that names the file and line, and so is a missing `--config` file, while a missing default file just means the defaults. (`--check`, `--scrape`, `--config` and `--print-config` cannot be set in the file, and a relative `output` is taken from the current directory, not the config file's.)
- [x] **Upload and download rate limits**: `--max-download-rate` and `--max-upload-rate` (`max-download-rate` and `max-upload-rate` in the config file) cap the piece data moved each way, in KiB/s across all peers of the session; 0, the default, means no limit and leaves the code path as it was. Each direction is one token bucket that holds a quarter second's worth as burst (at least one 16 KiB block), kept as the time it will be full again, so it needs no timer task. Bytes are taken from it before they move. A block request waits for its turn before it is sent, so the data it asks for is paid for in advance and arrives no faster than the limit, without reading slower or dropping anything. A block a peer asked us for waits likewise before it goes out, while the worker keeps handling the peer's messages, so a `Cancel` still drops a queued block. Each peer holds at most one reservation per direction and reservations are served in order, so peers take turns and a fast one cannot starve the rest; a reservation a peer can no longer use (it choked us, nothing is left to claim, our upload queue for it emptied, or it disconnected) is given back. A peer waiting for its turn with nothing in flight is not dropped for being silent, and since the request pipeline sizes itself to the measured rate, a throttled peer's queue shrinks to about 3 s of its share. Only block payloads count: message headers, requests, `Have`s and other protocol messages, and tracker and DHT traffic, do not. (The choker still ranks peers by the rate they actually delivered, so under a tight limit, where every fast peer gets the same share, its ranking says little and ties keep the order peers connected in. Bytes paid for a request that is then lost to a choke or cancelled in endgame are not given back. There are no per-peer or scheduled limits.) A limit can be changed while running (`Client::set_rate_limits`): debt taken on at the old rate is cut to one burst, reservations made before the change are made again, and peers waiting for their turn are woken at once. The new limits are not written to the config file; the terminal UI changes them with `d` and `u`.
- [x] **Several torrents in one session**: any number of `.torrent` files and magnet links may be given, and they are downloaded and seeded at once, each as a single torrent would be, until every one is done. They share a `Client`: one peer id, one listening port, one DHT node and one pair of rate limits, so `--max-download-rate` and `--max-upload-rate` cap the whole session. The port and the DHT node open the first time a torrent needs them, so, as before, a session of torrents that are all complete opens no port and one of private torrents runs no DHT node. Incoming peers go through one listener, which reads each handshake on a task of its own (at most 64 at a time) and hands the connection to the torrent whose info hash it names, if that torrent is taking peers yet, where it is answered or turned away as before; a peer for any other torrent is dropped unanswered. Each torrent's progress bar (and its hashing bar) is headed by its name, cut to 20 characters so the bars line up, and log lines are written above the bars rather than through them. With several torrents, each one's log lines carry its name, and work done for all of them, such as opening the port, is logged under `session`. One that fails, say because no tracker answered, is logged and the others carry on; the exit code is then non-zero, or 130 if Ctrl-C cut any short and none failed. Ctrl-C stops every torrent, and its handler is installed when the first torrent starts checking its data or, with nothing to check, announces. A torrent given twice runs once: the second is refused while the first runs. `--check` and `--scrape` handle each torrent in turn, under its name. (There is no limit on how many torrents run at once and no queueing of downloads. Torrents are added and removed while running from the terminal UI only.)
- [x] **Session-wide connection limit and hashing queue**: `--max-connections` (`max-connections` in the config file, default 200) caps the peer connections open at once across every torrent of the session, so ten torrents cannot run the process out of file descriptors; `--max-peers` stays the cap for each torrent. The `Client` holds the slots, a semaphore whose permit guard also wakes every torrent waiting for one when it is dropped. Every peer worker, whether we connected or the peer did, takes a permit before it starts and holds it until it exits, and a magnet's connections keep theirs when they pass from the metadata fetch to the download. A torrent that finds none free stops connecting out, and tries again as soon as any torrent frees one; a peer that connects to it meanwhile is turned away, as when it is at `--max-peers`, and a torrent with peers waiting for a slot does not conclude that it ran out of peers. The client also holds a hashing queue, a semaphore of one: torrents check the data already on disk one at a time (each on up to 4 threads), and a torrent that waits shows `queued for checking` on its bar. Ctrl-C ends the wait at once and stops a check at its next piece (`verify::verify` looks at a cancel flag between pieces), so the torrent ends as interrupted. (Slots are first come, first served, with no fairness between torrents beyond the per-torrent cap, so with many torrents wanting more than the limit, a torrent that started early may keep most of the slots. That is a known gap, and fine under the defaults, where 30 peers each for fewer than seven torrents stay under 200. `--check` is not queued.)
- [x] **Torrents that write the same file are refused**: before a torrent creates or reads anything, `Client::claim_files` records the path of each of its files (`Storage::paths`: the output directory made absolute, created first if need be, joined with the torrent's relative path, and lowercased on macOS and Windows, whose default file systems ignore case) against its info hash and name. If another running torrent already holds one, the newcomer fails with a message naming the file and that torrent, so it touches no file and writes no resume file, and the others go on unaffected. The claim lives in the torrent's `Claim` and is released when the torrent ends, so the files are free again for a torrent that starts later. `download_file` makes it right after the torrent claims its info hash, and a magnet link as soon as its metadata has arrived, before the metadata is saved. A torrent that lists one path twice (compared the same way) is rejected in `storage::layout`. `--check` and `--scrape` write nothing and make no claim. (Only torrents of one session are compared: another process, or a file that is a link to another torrent's, is not detected.)
- [x] **Terminal UI** (`ratatui`): on by default when stdout and stderr are terminals, off with `--no-tui` or `tui = false`, never with `--check`, `--scrape` or `--print-config`. The engine publishes cheap counters in `stats` (relaxed atomics, and short locks taken per piece or per announce, never per block): per torrent its state (fetching metadata, queued for checking, checking with its progress, downloading, seeding, pausing, paused, removing, done, interrupted, failed), bytes verified, received and sent, connected peers, what each tracker last said (now with seeders and leechers when it gives them), the peers each source brought and the pool's size; per peer its choke and interest flags, fast and pex support, client, bytes each way and pieces had. The UI pulls a snapshot four times a second, works out rates from the difference with earlier ones (smoothed over a second; the ETA over 30 s), and draws a header, the torrent table, a detail panel with peers (and the torrent's rate sparklines, or the selected peer's: with the panel focused, the Peers tab has a cursor that stays on its peer when the order changes and takes the nearest row when the peer goes), a piece map with the swarm's numbers, trackers (with the DHT, PeX and incoming peers), files and info tabs, a log pane and a key bar. Columns drop on narrow screens, down to 60×16. Logs go to an in-memory buffer of 1000 lines meanwhile, and the indicatif bars draw nothing. `d` and `u` change the rate limits, typed on an input line over the key bar, and the header shows them next to the rates. `p` pauses the selected torrent or resumes it, and the key bar says which. `x` removes it, after asking in a box over the screen that gives its file count and size: `y` keeps the files and `D` deletes them too. `a` adds a torrent, typed as a path (taken from the directory rtrnt started in) or a magnet link, and with no torrent given the UI starts empty, saying `press a to add a torrent`; without the UI a torrent is still required. Clicks select torrents and peers, sort by a column and switch tabs, and the wheel scrolls; `m` turns the mouse off so the terminal can select text. `q` or Ctrl-C stops the torrents as Ctrl-C does without the UI, and again quits at once; the terminal is restored on every way out, panics included, and the warnings and errors of the last 10 s are printed after. `cargo run --example tui_demo` shows a made-up session. (Gaps: added torrents and changed limits are not remembered by the next run, since there is no session file; peer graphs restart when the selected torrent changes, since only its peers' history is kept; there is no output directory per torrent, and `a` has no path completion.)
- [x] **Torrent manager**: `manager::Manager` owns the session's torrents. Each has an entry with its `Source` (now in the library, `source.rs`), its info hash (a `.torrent` file is loaded first) and its state: running with a stop of its own, paused, or ended with its outcome. A torrent stops on Ctrl-C or on its own stop. `Manager::run` keeps the tasks in a `JoinSet`, carries out the UI's commands (the rate limits, and adding, pausing, resuming and removing a torrent) and ends once no task is running and the command channel is closed, with the exit codes as before. The UI's last line says `nothing running, press q to exit`. A pause sets the torrent's own stop, so it ends through the interrupt path (tracker `stopped`, workers drained, resume file saved, connection slots and file claims freed), and the manager marks it paused; a resume runs it again from its source, so the resume file skips the hashing and a magnet link uses its saved `.torrent`. A finished or failed torrent can be resumed too. The torrent's new stats take its old row's place and carry the earlier runs' downloaded, uploaded and active time, while the tracker hears the new run's counts; the seed ratio counts the earlier uploads. A torrent paused when the session ends exits 130. Removing one stops it as a pause does if it runs, with its row showing removing (which the end of its task does not turn into paused), then drops its row and its entry, so it counts for nothing in the exit code. With `delete`, on the blocking pool, `storage::delete_files` removes the files its layout lists (paths that `layout` keeps under the output directory) if they are regular files with no symbolic link among their directories, then the directories left empty up to the torrent's own, never the output directory; then the resume file and a magnet link's saved `.torrent` go. Nothing is deleted while a running torrent claims one of the files, and failures are logged and shown as a notice. Without it the resume file stays. An added torrent is loaded first (a `.torrent` file read on the blocking pool, in the manager's loop, so two adds of one torrent cannot race) and refused with a notice, making no row, if its file does not load or the session has it already: running, paused (`press p to resume`), ended or being removed. Otherwise it starts as one given at startup, and a file another torrent writes still fails its row. With the UI on, each torrent's logs carry its name and a failure is logged as it comes, as with several torrents, since more can be added. The function that runs a torrent is a parameter, so the unit tests use a fake one.
